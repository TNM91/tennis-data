# Face ID sign-in on iPhone

Face ID is an optional, explicit way to sign in. The signed-out welcome screen shows a button only after the user saves an account in Account settings. Opening or foregrounding an already signed-in app never presents a lock or biometric prompt. The previous app-lock flag is removed on launch; it does not opt anyone into credential storage.

Setup requires the current TenAceIQ password. The primary client verifies its current user, and an isolated, non-persistent Supabase client verifies the password against that same account ID. Only then does the native plugin request biometric approval and save the email, password and account ID in one private Keychain item. The verification session is revoked afterward. No password is saved to UserDefaults, Web Storage, a file or iCloud. The item uses `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly` and `biometryCurrentSet`, so changing enrolled biometrics or removing the device passcode makes the saved item unavailable. UserDefaults contains only the saved account ID for prompt-free status checks.

Tapping Sign in with Face ID authenticates and retrieves the saved credential with a fresh LAContext. Keychain reads run off the UI thread. An isolated Supabase client performs a fresh password sign-in; the returned account ID must match the saved ID. The primary client adopts the tokens only while the signed-out visit is still current and no account is already signed in. An abandoned or wrong-account verification session is revoked. A successfully adopted session must not be revoked by temporary-client cleanup. Invalid credentials remove the stale shortcut. Password and email-code sign-in remain available.

Logging out still revokes and removes the ordinary account session. The explicitly saved Keychain shortcut remains until Remove saved sign-in, replacement by another account, or a confirmed account-deletion request. Deletion only removes a shortcut belonging to the requesting account. Backgrounding or leaving a sign-in/setup view cancels pending authentication; request and generation guards reject late callbacks. No foreground observer, privacy window or app-lock shield remains.

Validation: `node --test mobile/scripts/ios-app-lock.test.mjs mobile/scripts/ios-purchases.test.mjs`, `node mobile/scripts/app-lock-ui-smoke.mjs` after bundling, and the Mac simulator workflow. The retained app-lock filenames provide packaging compatibility; their assertions now require sign-in behavior. Chromium/WebKit use synthetic auth and native responses. The unsigned simulator runs real native lifecycle and bridge code with an injected authenticator/vault; the actual Security-framework helpers still compile. Test probes are absent from signed Release source. A physical iPhone must still verify the actual Face ID scan and secure Keychain retrieval after installing the beta.

The app-owned privacy manifest continues to declare UserDefaults reason CA92.1 for the app's own setting. Preparation registers it as an App resource; package verification checks it along with the new sign-in purpose string.

Apple references: [biometric Keychain access](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id), [current biometric enrollment](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset), [required-reason APIs](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api).
