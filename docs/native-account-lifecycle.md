# Native accounts and reviewed permanent deletion — build 150 candidate

Status: implementation under review. **Do not apply the migration or activate native account creation until the owner approves both the private database changes and staffing the seven-day manual erasure process.** This is not automatic account erasure or a claim of public App Store readiness.

## Product scope

The iPhone welcome offers an email code for a new Free account or an existing account, alongside password sign-in. Supabase generates/verifies the code; the existing Resend service delivers it without an auto-verifying link. New accounts use the existing member-profile trigger and inactive paid-subscription defaults. The code request never changes a password, linked player, paid role or subscription. Terms acknowledgment is required before signed-out requests. Codes, provider keys and account tokens never appear in API responses or application logs. Provider-side OTP expiry and verification-attempt controls remain required; verify their configured values before public launch.

A visible Account header button opens settings without leaving the native app. Password recovery retains the existing verified recovery path. Existing web billing opens only an authenticated Stripe-hosted portal URL. This does not introduce iPhone purchasing or establish a compliant storefront/payment strategy.

In-app permanent deletion requires a fresh Auth identity, a verified email and a password/OTP AMR timestamp within ten minutes. Refresh-token issuance time does not count. An older session can read its request status and verify its fixed current email before requesting deletion. Typed DELETE submits an idempotent request, displays the original deadline/reference, and does not claim immediate erasure or cancel billing. An uncertain write is recovered by reading status before another attempt.

Code verification occurs in a separate nonpersistent client. A closed or superseded visit does not apply its late response to native secure account storage. Successful verification is applied to the main client only after checking the current visit, expected email and, for reauthentication, exact current owner. Private settings and billing responses recheck ownership before presentation/opening. State is in memory and clears on account/screen disposal.

## Migration and access

`supabase/migrations/20261028000100_native_account_requests.sql` adds only:

- `account_deletion_requests`: exact account UUID, verified delivery email, status, request/deadline timestamps and reviewer until completion; completion clears the UUID/email and retains a minimal request/timestamp audit record. No Auth FK, so the delivery receipt can finish after account removal.
- `native_email_auth_limits`: SHA-256 email/IP counter keys (pseudonymous, not anonymous), three fixed windows and a timestamp. No raw email/IP, OTP or token is stored here. One request/email/minute, five/email/hour, five/IP/15 minutes; one bounded cleanup of up to 100 entries older than two days on accepted requests. No cron or retry loop. At most three counters per accepted address/IP pair.
- Four service-only invoker functions for readiness, rate limits, own request/status and current-admin review. Direct PUBLIC/anon/authenticated access is revoked; RLS is enabled without client policies. No existing grants, rows, FKs or ownership rules change. The service receives no new permission to delete an Auth account or existing user records.

Missing migration/configuration fails closed before creating an Auth record or delivering a code. Admin API verifies the caller remotely and rereads its current admin role; the SQL function independently checks that role. The UI gate is not the security boundary. Requests are fetched explicitly, oldest deadline first, 25 at a time. No background polling, local storage, automatic email or destructive job.

## Owner decision before activation

The proposed promise is **manual permanent erasure within seven calendar days, with completion email**. An accountable administrator must check `/admin/account-deletions` every day and finish requests before their displayed deadline. A backup administrator is needed if the requester is the only current administrator or the owner cannot operate the queue. Do not enable this promise without that operating capacity. An approval of beta builds alone does not approve this policy or production permission changes.

The request does not suspend access immediately. Erasure processing must handle access and outstanding sessions before removal. Billing must be reviewed and continuing charges addressed; this candidate does not cancel Stripe or Apple subscriptions. Never mark a request completed just because it was reviewed, deactivated or removed from Auth.

## Manual erasure procedure — per-account, separately authorized

This is an investigation/checklist, **not a bulk-delete script**. A real production account deletion and any subscription cancellation require their own explicit authorization. Do not copy customer addresses, tokens or personal evidence into public PRs, screenshots or logs.

1. Start review for the stored request. Match the exact stored account UUID and verified email in authorized administration tools. Record private evidence and the deadline; do not use a caller-supplied UUID or a name match. Do not require the requester to email/call to initiate deletion.
2. Snapshot current schema metadata and build an exact-account dependency/retention plan before changing data. The October 28 read-only catalog audit found 170 direct Auth/profile foreign keys, 174 ownership/meta columns and eight Storage buckets. These counts are audit scope, not a proven exhaustive erasure algorithm. Recheck current schema and application-only ownership links.
3. Resolve shared ownership without silently destroying teammates' records. Known blockers include `clubs.owner_user_id` (RESTRICT), `season_availability_invites.created_by`, `team_chat_rooms.created_by`, `team_chat_polls.created_by` and `team_chat_poll_votes.profile_id` (NO ACTION). `internal_conversations.created_by_user_id` cascades from profiles and can remove other members' history. Clubs, group clinics/templates and shared sessions have creator/updater cascades that require explicit preservation/transfer decisions. Do not weaken a constraint or grant access as a deletion shortcut.
4. Erase the requester's associated personal data and user-generated content, including team/internal messages, media copies, training notes/proofs, personal goals, uploads/import artifacts, account/team contact details, notification registrations, relevant invitations and histories. Include owner columns without a declared FK, such as `product_usage_events.user_id` and `upgrade_requests.requester_user_id`. Independently collected public match/player records require provenance-based review; do not claim all public tennis history will be erased. Financial/legal retention, including `stripe_billing_events.profile_id`, requires a specific justified retention decision and minimization; it is not a blanket exception for personal content.
5. Review subscriptions in the actual provider, address continuing charges/refund handling as authorized, and preserve only required financial records. This queue never cancels subscriptions. Do not start a native purchase integration as part of erasure.
6. Inspect Storage metadata **and actual object paths**, including null owner IDs. Erase exact personal objects/copies through the Storage API so blobs are actually removed; deleting `storage.objects` rows alone is not erasure. Personal buckets include `profile-photos`, `data-assist-screenshots`, `personal-quest-photos`; paths commonly begin with account UUID. `team-room-files` paths use room UUID / owner UUID / file. Review `tiq-league-photos`, `club-branding`, `tennisrecord-source-pages` and `maintenance-archives` for shared assets, duplicates, retention and restoration handling. Do not blindly purge a whole bucket or rely on owner_id alone. Auth deletion can be blocked while owned objects remain.
7. Handle outstanding sessions and account access. Revoking refresh sessions does not invalidate every unexpired stateless JWT; establish an exact-account access block or wait for verified expiry and prove relevant service/private reads are denied before certifying completion. Do not shorten global JWT settings or change everyone else's access. This candidate adds no universal deleted-account denylist. Remove the exact Auth account only after the reviewed dependency/Storage plan is completed, through already authorized administration tools. Verify both Auth and profile absence; recheck residual owner keys, personal content, files and shared-record preservation. Preserve a controlled non-production case to prove the complete procedure before public launch.
8. Only after completing the erasure, check all six evidence boxes in the queue: personal data, files, billing, retention, sessions and shared data. The admin endpoint refuses completion if the exact Auth user still exists, Auth lookup fails, a profile remains, known non-FK usage/upgrade rows remain, or known owned/path-matched personal Storage metadata remains. Those mechanical checks are additional guards, not proof of every relationship's erasure.
9. The first successful erasure verification records `erased`. The existing Resend provider must accept the completion email before the request becomes `completed` and clears UUID/email. Provider failure retains the address and an honest confirmation-pending state. Retry explicitly with the same request ID; a stable provider idempotency key protects ordinary retries within the provider's retention window, not exactly-once delivery forever. An accepted email is not evidence of inbox delivery; investigate bounces privately. If final recording fails after mail acceptance, retry the same request; never perform the account erasure twice.

## Verification and release boundaries

Positive QA is local/synthetic only: mocked Auth/email/billing, native production bundle, real PostgreSQL-compatible migration tests and route authorization tests. No real signup, code email, billing session, cancellation, deletion request, user erasure or completion email has been executed. Production catalog audit reads schema/configuration only.

Before release: full repository verification, native guards/bundle/iOS checks, exact-head required CI, then owner approval of migration and operating policy. Apply the exact reviewed SQL once, verify function definitions/RLS/grants/empty new tables and preservation of existing permissions, then use standing beta approval for the verified build. No manual Vercel rebuild or paid preview is required. An anonymous bounded production smoke can prove the new routes reject unauthorized callers; it cannot establish positive signup/email/erasure behavior.

Before public App Store submission: a separately authorized controlled account must prove real delivery, six-digit OTP/provider configuration, new Free profile defaults, recent reauthentication, exact deletion request, full manual erasure, old-token access handling, shared-data preservation, billing handling and completion delivery. Reconcile published privacy/retention and Terms with actual operations, finalize storefront/purchase/restore behavior, and complete physical iPhone/VoiceOver/Dynamic Type acceptance. Public submission remains separately authorized.
