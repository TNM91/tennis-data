# Native Captain tools

My teams shows Captain only when the current accepted team-room payload reports captain/co-captain authority. The server separately enforces Captain account entitlement through the shared Captain API authentication, then checks an exact unarchived accepted team/league/flight captain link and current room participation. A forged client tab cannot authorize access. Ambiguous duplicate accepted links fail closed. The existing captain removal exception matches team chat.

The native read endpoint returns a bounded roster, upcoming schedule and only the current account's saved lineup drafts. It never returns invitation/response tokens, contact phone/email, other captains' private notes, or storage links. Roster uses the existing exact-scope roster loader (250 maximum); schedule reads 41 head rows over the next 120 days and displays up to 40 after shared calendar filtering; drafts read 21 and display current matches from the latest 20. Court detail is capped at 30 courts/two names each. Incomplete lineups retain the shared Working/not-sent classification.

Week opens fixture-specific availability only on an explicit tap, through the existing Captain summary service. The app confirms returned fixture ID/date/opponent and exact team scope. Same-day fixture ambiguity fails closed rather than mixing answers. Counts and selected-player labels derive from the bounded people list, with player/season/captain/saved reply sources and the existing double-header omission notice.

Roster search and saved-lineup review run in memory. Captain subtabs share one loaded snapshot; there is no idle polling, extra subscription, persistent cache or automatic retry. Intentional entry/refresh reads the workspace once. Team/session disposal clears the snapshot and ignores late replies; backgrounding clears the Captain panel and reloads on foreground. Ordinary chat draft state remains independent. Week → Plan lineup opens a private editor for an upcoming fixture. Saved-lineup review offers Edit when one upcoming fixture matches. Captains can add/remove up to 30 singles/doubles courts, assign current roster players once, mark an empty court as defaulted, and save location, arrival, directions, match notes and private notes. Saving is separate from publishing; Review team publishing shares a proposed lineup, shows shared court confirmations and sends the confirmed final update.

Runtime: one explicit workspace read performs account/accepted-link/room checks, then the bounded roster, schedule and draft reads in parallel. Availability summaries use the existing bounded service only on request. No cron, refresh cadence, paid feature, provider, database migration, grant or user notification is added. Synthetic UI checks block external requests; production checks use only anonymous/unlinked QA denial and never change actual team data.

## Private lineup editor

GET/PUT `/api/mobile/captain/lineup` share the exact accepted Captain scope and account entitlement checks. Every operation rechecks the upcoming uncancelled, uncompleted fixture (next 120 days) and bounded current roster. Saved drafts are owner-only, exact team/league/flight/date/opponent; multiple competition-layer plans or a different selected fixture fail closed. New/date-only plans also require a unique same-opponent fixture that day; fixture-linked plans retain their exact ID. A roster row key is never used as a player UUID: unlinked players save by name with an empty player ID. Assignments no longer on the roster must be replaced before saving.

Existing writes compare the displayed `updated_at` in the database update. Creation uses insert with the owner/scope unique constraint; no unconditional upsert. Exact desired-state retries confirm without changing delivery or writing twice, including a lost first response. A conflict never replaces the newer plan. Untouched opponent scouting/manual-roster/scenario fields stay intact on updates. A changed plan becomes Working/not sent; existing chat announcements and receipts are not modified. This endpoint never sends a message, availability invitation or notification.

The editor keeps changes only in memory. Uncertain saves freeze the submitted plan and offer an explicit identical retry; definite validation failures allow corrections, while access/conflict errors require reopening. Text remains selectable for retaining notes. Leaving the team/session/background disposes the editor and ignores late results. Close warns before discarding unsaved changes. One explicit editor open reads access, fixture, roster and draft (plus one bounded same-day fixture read for new/date-only plans); one explicit save repeats those checks and performs at most one conditional mutation. No polling, persistent drafts, new service, migration or paid feature is introduced. Synthetic UI tests block external requests; production smoke uses only unauthenticated/unlinked denials and never writes actual team plans.

## Team publication and confirmed final send

Captain → Week → Review team publishing is an explicit bounded read of the saved plan and existing team-room summary. Captain account entitlement, one exact accepted team/league/flight link, current participation and the upcoming fixture are rechecked. Native publication requires a single team fixture for the date because shared cards and legacy response sources are date based; ambiguous/duplicate cards fail closed. Up to 12 complete courts are supported by shared cards, with distinct labels and unambiguous roster names. The review includes only public court names, arrival time and location. Private notes, match notes, directions, roster IDs and availability URLs are not copied into new card content.

`publish_native_lineup` constructs the card from the current owner draft on the server. The displayed draft version and a digest of current shared metadata must match. Existing cards update with metadata CAS and new cards use a deterministic conversation/date ID. The committed card stores the publication ID/owner/draft version. An identical replay or already-identical proposal skips all defaults, conversation updates and notifications. Only the write winner runs those effects. Notifications are best effort: a crash after commit can miss an alert; retries never repeat effects. No notification outbox, automatic retry, polling, cron or new paid service is added. Native-only protection does not change the website proposal path. A final receipt blocks proposal replacement; the separate captain replacement/change workflow remains follow-up work.

Native `send_final_lineup` uses the shared server readiness, active card, locked lineup ID, and the reviewed metadata digest. It cannot infer readiness from a private draft or override player responses. The existing final-receipt CAS claims one announcement ID. Native recovery checks the stored claim and actual announcement; an interrupted send completes using that original ID, not a fresh post. Only an inserted announcement triggers recovery alerts. Superseded claims fail closed. Pending delivery is recoverable from a reopened review when courts remain confirmed. A delivered receipt confirms a retry without another announcement or alert. The unchanged matching owner draft is marked Final/sent with its own version CAS; different or newer private plans are left intact.

The in-memory review freezes one intent on an uncertain response, disables the other action and offers only an explicit identical retry. It clears on team/session/background disposal and ignores late responses. No real team card, draft status or notification is changed by verification: fixtures block external requests, helper/API tests use mocks, and bounded production smoke checks only anonymous and unlinked QA denials. Physical owner acceptance remains pending.


## Replacement replies in Match day

The native Match day view now shows a sent replacement request with the court, outgoing/replacement names, new court, deadline and answer. Only the linked replacement receives reply controls; display-name matching alone cannot authorize a native reply. The current active card and a digest of the exact displayed shared metadata are checked before any reply write. An answered, pending, completed, changed or superseded request fails closed.

A metadata CAS claims the response before availability, versioned acknowledgment, reminder cancellation or manager alerts. The stored native reply token/actor/choice permits an identical interrupted retry to repair idempotent follow-up writes without repeating manager alerts. A conflicting choice cannot overwrite the newer card. Published-change acceptance also checks the actual undeleted change announcement before restoring a final receipt. Alerts remain best effort, so interruption after the claim can miss a captain alert. No background retry, new table, polling or paid service is added. Native captain selection/publication of replacements remains follow-up work; these replies work with replacement requests sent through the existing captain workflow. Physical linked-player acceptance is pending.


## Captain published replacements

Captain → Week → Replace lineup player reads the exact fixture, current shared card and bounded roster behind Captain account entitlement and the existing exact accepted-team/participant checks. A delivered final (including an accepted delivered replacement) is required. A declined delivered replacement can be replaced again. Pending delivery or an unanswered request blocks another change. Ambiguous roster names, assigned replacements, defaults, stale tokens, duplicate-date cards and invalid shared courts fail closed.

The captain chooses one outgoing assigned player and one unassigned current roster player. The preview shows the changed pairing. Sending replaces only that seat in the shared court; other courts, defaults, time/location and private owner drafts remain unchanged. The source card is updated with metadata CAS, a higher lineup version, a replacement notice and a fixed announcement UUID. The previous final receipt is cleared until the replacement accepts. Ordinary native proposal/final publishing cannot bypass the outstanding change.

A pending claim is retained after an ambiguous write or announcement insertion. An identical manual retry verifies the committed intent and unchanged court plan, inserts/confirms the same announcement ID, then opens replies using another metadata CAS. Reopening the review recovers a pending request for its original captain. A superseded claim is never replayed into the newer plan. This is a guarded sequence across existing tables, not a database transaction; competing legacy website edits can produce conflicts requiring refresh. No new outbox, polling or paid service is added.

Only the winner opening replies attempts alerts. Recipients are the affected outgoing player, replacement and retained partner who have current unarchived accepted links, current participation, alerts enabled and no block of the captain. Removed members (with the existing captain exception), other flights, ambiguous linked names and unrelated players are excluded. Existing web push and Apple push are used; lock-screen text stays generic. A crash after commit may miss an alert; retries do not duplicate alerts. No real lineup or test alert is changed by verification. Physical owner/player acceptance remains pending.

A successful native proposal/final/replacement send explicitly refreshes the conversation once and marks Match day for a fresh bounded read when opened. It does not rely only on a timely realtime event to show the changed court.
