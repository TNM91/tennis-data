# Native Captain tools

My teams shows Captain only when the current accepted team-room payload reports captain/co-captain authority. The server separately enforces Captain account entitlement through the shared Captain API authentication, then checks an exact unarchived accepted team/league/flight captain link and current room participation. A forged client tab cannot authorize access. Ambiguous duplicate accepted links fail closed. The existing captain removal exception matches team chat.

The native read endpoint returns a bounded roster, upcoming schedule and only the current account's saved lineup drafts. It never returns invitation/response tokens, contact phone/email, other captains' private notes, or storage links. Roster uses the existing exact-scope roster loader (250 maximum); schedule reads 41 head rows over the next 120 days and displays up to 40 after shared calendar filtering; drafts read 21 and display current matches from the latest 20. Court detail is capped at 30 courts/two names each. Incomplete lineups retain the shared Working/not-sent classification.

Week opens fixture-specific availability only on an explicit tap, through the existing Captain summary service. The app confirms returned fixture ID/date/opponent and exact team scope. Same-day fixture ambiguity fails closed rather than mixing answers. Counts and selected-player labels derive from the bounded people list, with player/season/captain/saved reply sources and the existing double-header omission notice.

Roster search and saved-lineup review run in memory. Captain subtabs share one loaded snapshot; there is no idle polling, extra subscription, persistent cache or automatic retry. Intentional entry/refresh reads the workspace once. Team/session disposal clears the snapshot and ignores late replies; backgrounding clears the Captain panel and reloads on foreground. Ordinary chat draft state remains independent. Week → Plan lineup opens a private editor for an upcoming fixture. Saved-lineup review offers Edit when one upcoming fixture matches. Captains can add/remove up to 30 singles/doubles courts, assign current roster players once, mark an empty court as defaulted, and save location, arrival, directions, match notes and private notes. Saving is separate from publishing; confirmed team-chat publication remains follow-up work.

Runtime: one explicit workspace read performs account/accepted-link/room checks, then the bounded roster, schedule and draft reads in parallel. Availability summaries use the existing bounded service only on request. No cron, refresh cadence, paid feature, provider, database migration, grant or user notification is added. Synthetic UI checks block external requests; production checks use only anonymous/unlinked QA denial and never change actual team data.

## Private lineup editor

GET/PUT `/api/mobile/captain/lineup` share the exact accepted Captain scope and account entitlement checks. Every operation rechecks the upcoming uncancelled, uncompleted fixture (next 120 days) and bounded current roster. Saved drafts are owner-only, exact team/league/flight/date/opponent; multiple competition-layer plans or a different selected fixture fail closed. New/date-only plans also require a unique same-opponent fixture that day; fixture-linked plans retain their exact ID. A roster row key is never used as a player UUID: unlinked players save by name with an empty player ID. Assignments no longer on the roster must be replaced before saving.

Existing writes compare the displayed `updated_at` in the database update. Creation uses insert with the owner/scope unique constraint; no unconditional upsert. Exact desired-state retries confirm without changing delivery or writing twice, including a lost first response. A conflict never replaces the newer plan. Untouched opponent scouting/manual-roster/scenario fields stay intact on updates. A changed plan becomes Working/not sent; existing chat announcements and receipts are not modified. This endpoint never sends a message, availability invitation or notification.

The editor keeps changes only in memory. Uncertain saves freeze the submitted plan and offer an explicit identical retry; definite validation failures allow corrections, while access/conflict errors require reopening. Text remains selectable for retaining notes. Leaving the team/session/background disposes the editor and ignores late results. Close warns before discarding unsaved changes. One explicit editor open reads access, fixture, roster and draft (plus one bounded same-day fixture read for new/date-only plans); one explicit save repeats those checks and performs at most one conditional mutation. No polling, persistent drafts, new service, migration or paid feature is introduced. Synthetic UI tests block external requests; production smoke uses only unauthenticated/unlinked denials and never writes actual team plans.
