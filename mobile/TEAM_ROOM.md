# Native team chat milestone

## Candidate behavior

My teams opens Conversation first, alongside Match day and Members. It reuses the existing accepted-team membership and removed-member checks. The navy conversation has a bounded scrollable history, reply previews, captain announcement labels, and a composer. Text and reply context stay in memory while switching the team's tabs or refreshing. Team changes and disposal clear drafts; no private draft enters local storage. Incoming text updates use one content-free Supabase signal subscription for the currently open team while the app is in the foreground. The server rechecks accepted scope, participation and removals before returning moderated text. Backgrounding, leaving the room or signing out closes the subscription. There is no idle API polling or presence traffic; failed connections wait for foreground/online/manual retry.

Text posts and replies use the fixed HTTPS Team Room endpoint through CapacitorHttp with the current owner's bearer session, disabled redirects, and 12-second connection/read timeouts. A native send receives one UUID v4. Uncertain responses lock its payload and offer retry with the same ID; simultaneous taps do not create another send. Success must confirm the exact ID, own-message flag, and text before clearing the draft. A retry after an uncertain response preserves the pending ID even if authentication subsequently fails. Discard retry explicitly warns that the original post may already exist. Navigation/sign-out clears transient state and suppresses late results; a user manually retyping a discarded post is outside automatic retry protection.

The server's existing primary key arbitrates concurrent sends. Duplicate responses require matching conversation, sender, text, kind and reply; edited/deleted/conflicting posts fail closed. Replays do not repeat notifications. This guarantees at most one inserted message per retained ID, not guaranteed notification delivery if the first request saves then fails before notifying. Website sends without an ID retain their legacy send semantics.

## Connected safety

The candidate includes private reports with four reasons, per-account blocking/unblocking of chat posts, and an Admin review queue at `/admin/team-chat`. Current membership is checked before reporting or changing block settings. Report content and author are derived from the selected room's stored message, not supplied by the client. Duplicate reports from the same reporter for the same post do not overwrite the existing review record. Only verified existing admins can load the bounded queue or resolve/remove a reported post. Removal is a soft deletion scoped to the report's stored message, room and author; the reviewer and time are recorded.

Blocked message text, reply targets and attachment/card metadata are redacted before the room payload is assembled, including website room reads. Ordinary chat notifications from that sender are suppressed for the blocker. Blocking does not remove either member from the team or prevent the group from seeing the blocker's posts; match workflow notifications outside ordinary chat may still arrive. Existing historical notification records are not retroactively removed. There are no claims of direct messaging, complete notification erasure, automated content filtering, or push delivery in this candidate.

## Foreground updates and read checkpoints

The lightweight `/api/team-rooms/chat` endpoint returns the latest 75 moderated messages, current account blocks and that account's read checkpoint. It does not create rooms, upsert rosters, sign files or recompute match plans. The separate route fails closed if an older website is restored. Full native room reads use `read=0`; website defaults remain unchanged. Match day data refreshes on intentional entry after chat updates rather than on every chat event.

Live history updates retain the actual composer DOM, draft, caret and focus. Older-history readers keep their visible message anchor when the bounded window advances. New-message counts cover only visible, nonblocked, nondeleted messages from others within the loaded 75, not all teams or unlimited history. Latest clears that room's count. Read acknowledgments occur only in foreground Conversation at the latest messages; the server derives the checkpoint from a real message in the exact room and updates only the current participant monotonically, preserving timestamp microseconds. Other members' read checkpoints are not exposed.

## Helpful and Celebrate reactions

The native candidate adds Helpful and Celebrate using the existing website reaction records. Formal lineup acknowledgments remain separate. The API verifies the accepted exact team scope and participation before selecting a live message in that conversation. Each request sets the desired state; repeated adds use conflict-ignore and repeated removals target only that owner, message, room and kind. Ambiguous responses retain the same desired choice for retry. Reactions send no push or email.

The service-only aggregate returns counts and the current owner's selected state for at most 75 message IDs. ## Native photo candidate

My teams offers Choose photo and Take photo through the pinned official Camera plugin. Selection opens a preview with Remove photo and an optional caption; only Send photo uploads it. Camera/library permissions are requested by the OS on explicit selection. The app does not save captures to the gallery. Canvas reduction creates a JPEG up to 1600 pixels and 2 MB; the server independently validates still-image bytes, pixel bounds and size, rotates and re-encodes to strip metadata including location. JSON requests are bounded while streaming to 2.9 MB rather than trusting Content-Length.

The existing private `team-room-files` bucket is reused with no new grants, storage service or cron. Each retained send UUID has one immutable room/owner object key. A duplicate object must match the normalized byte hash; message replay must match owner, room, body, reply and photo hash and must not be edited/deleted. Unknown insert results preserve the same object for retry rather than deleting an object another successful request may reference. An abandoned failed send can retain one private object; automatic garbage collection is not introduced in this milestone. File sends do not repeat notifications on confirmed message replay. A save followed by failure before notification still has best-effort notification semantics, as text sends do.

Native photo viewing is on demand through bearer-authenticated actions, with accepted exact team scope, current participation/removal and blocked-author checks before storage download. The app uses bounded JPEG data in an in-memory dialog; it does not use public or signed image links. Backgrounding, leaving the room, disposal or a live removal/block clears the viewer. Native full-room reads no longer mint attachment signed URLs; existing website attachment links retain their previous expiry semantics. Legacy image attachments over 2 MB remain available through the website rather than this native viewer. PDFs remain website attachments. Reports and soft removal reuse current moderation; the admin report queue retains caption text and removal controls, without a new image-review permission.

Runtime bound: no image downloads on chat refresh; opening one photo downloads at most one private stored image and returns a normalized JPEG up to 2 MB. No message bodies, images or device file paths enter logs or persistent draft storage. Synthetic phone checks cover preview, caption, explicit send, lost-response retry with one saved message, viewer and narrow layout; no real photo, post or notification is sent. Physical iPhone camera/library permission and capture behavior remain beta device acceptance checks.

## Inline photo previews

The next native candidate displays photos directly in Conversation, with a tap reserved for the full-screen viewer. Visible photo bubbles request a 320-pixel JPEG through the same bearer-authorized message read; the response is capped at 96 KB. No public or signed preview links are created. The backend still validates team access, current participation, blocks and deletion before downloading and decoding the stored photo.

IntersectionObserver loads only photos in the conversation viewport, at most two requests at once. A memory-only cache holds at most 24 thumbnails (about 3 MB of base64 at the response cap), avoiding downloads when live text/reaction updates rebuild the same history. Offscreen photos do not fetch. Backgrounding, team changes and disposal clear the cache and remove rendered private images; removed/blocked photo bubbles prune cached results, and late results cannot paint a different room/session. Failed thumbnails wait for an intentional full-photo tap or lifecycle retry, with no idle retry timer. Each uncached thumbnail still reads the underlying private photo (up to 2 MB) from storage; thumbnail sizing reduces transfer to the phone, not that storage read.

## Per-team alert controls

Members includes Mute team alerts / Turn team alerts on. This reuses the current participant mute flag, which filters ordinary chat push and existing team-room notification recipients, including team match reminders. It does not change Apple notification permission, another team, or another member. Muted members can continue reading and posting. There is no new table, grant, subscription, polling or external service.

The native action first resolves the exact accepted team and checks participation/removal without room creation or roster synchronization. A strict boolean update targets only that room and current account; success requires the stored participant and state. Retries retain the same desired state after ambiguous transport results. Team/session changes discard late confirmations and pending UI state. The saved setting remains server-side across devices; changes on another device appear on intentional full team refresh rather than a new preference subscription. No real team setting is changed by agent smoke tests.

## Team-coordination batch

Match day reuses the existing server availability, lineup acknowledgment, final-lineup-seen and arrival workflows. Native requests add an explicit marker: accepted exact room membership and current uncompleted card are checked before the shared action handler. A lineup acknowledgment carries the displayed version; availability does not implicitly acknowledge an unseen lineup. Final seen and arrival continue to enforce current publication and assigned-player checks on the server. A confirmed action intentionally reloads full match-day state. Uncertain responses retain the same action/target/version; no automatic retry timer or polling is added. Normal sequential retries of unchanged availability/review avoid duplicate manager notifications; notification delivery remains best-effort and simultaneous independent devices can race.

Conversation search filters the latest loaded 75 moderated messages by body or sender in memory. It performs no API requests, persists no query, excludes removed bodies, and suppresses read advancement while a filter is active. Live history refreshes retain the query and actual composer DOM.

Own ordinary text/photo posts expose Edit and Remove. Dedicated native actions check current accepted participation and exact room/owner. Formal announcements, match cards and unknown workflow metadata are excluded. Conditional updates match original body, edit timestamp and metadata; conflicting newer changes fail closed. Identical saved edits/removals can be replayed without another write. Removal is a soft message marker; private attachment objects and metadata are retained for moderation, while normal message/photo reads reject the deleted post. No purge, new grant or storage policy is introduced. The editor closes and clears on background/team/session disposal; uncertain retries freeze the same payload.

Verification uses synthetic auth/data and blocks external browser requests. No real RSVP, arrival, acknowledgment, edit/removal, chat post or notification is sent by agent testing. Real iPhone keyboard and match participation remain beta acceptance checks.
